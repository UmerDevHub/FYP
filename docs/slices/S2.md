# Slice S2: Login and accounts (on top of the 35%)

Status: not started
Size: 5 days (Estimate). Server: Umer. Screens: Habib (Proposal).
Read first: docs/progress.md, docs/architecture.md (section Login), docs/api-contract.md (S2), docs/design.md.

## Goal
A visitor can register as a customer, log in, stay logged in after a reload, log out, reset a forgotten password and change their own details. Every later slice stands on this.

## Use cases
UC-01 Register Account, UC-02 Log In and Log Out, UC-03 Reset Password, UC-04 Manage My Account.

## Requirements (word for word from the SRDS)
- FR-AU-01 Customer registration. The system shall allow a visitor to register as a customer
  by entering name, email, phone number and password. The email address shall be unique. The
  role of a self-registered user shall always be Customer. [Phase 1; UC-01]
- FR-AU-02 User login. The system shall authenticate a user with email and password. If the
  details are wrong or the account is inactive, the system shall show one general error
  message that does not reveal which detail was wrong. [Phase 1; UC-02]
- FR-AU-03 Session handling. The system shall keep the user logged in with a short- lived
  access token and a renewable refresh token. Logging out shall cancel the refresh token.
  [Phase 1; UC-02]
- FR-AU-04 Password reset. The system shall send a one-time reset link to the registered
  email. The link shall expire after a fixed time and shall work only once. [Phase 1; UC-03]
- FR-AU-05 Profile management. The system shall let a logged-in user view and update name and
  phone number, and change the password after entering the old password. [Phase 1; UC-04]
- FR-AU-06 Role-based access control. The system shall check the role of the user on the
  server for every protected operation and shall refuse operations that the role is not
  allowed to perform. [Phase 1]
- FR-AU-07 Branch restriction. The system shall limit Sales Staff and Branch Managers to the
  records of their own branch for sell requests, inspections and vehicle management. Inventory
  viewing across branches is allowed for Branch Managers (FR-IV-01). [Phase 1; UC-14, UC-23,
  UC-24]
- FR-NT-01 In-app notifications. The system shall create an in-app notification for the events
  listed in the Notification Events table in Section 3.1.12 and shall show the unread count. A
  user shall be able to mark one or all notifications as read. [Phase 1; UC-04]
- NFR-SC-01 Every user except a visitor shall log in with email and password. Passwords shall
  be stored only as salted hashes made with a recommended password hashing algorithm and shall
  never be shown or logged.
- NFR-SC-04 Access tokens shall be short-lived. Refresh tokens shall be stored in an httpOnly
  cookie, shall be renewed on use and shall be cancelled on logout and when an old token is
  reused.
- NFR-SC-06 Login, registration, password reset, upload, price estimate and chatbot requests
  shall be rate limited. Repeated failed logins may lock the account for a short time
  (assumption A-18).
- A-18 A user is locked for a short time after five failed logins.

## Rules for this slice
- Left out on purpose: two-factor login, Google login, e-mail verification, "remember me". They are not in SRDS Phase 1.
- Proposal: access token 15 minutes in memory only. Refresh token 7 days in an httpOnly cookie, stored hashed with a family id, renewed on every use. A used token that is used again cancels the whole family.
- Proposal: bcrypt cost 12. Password 8 to 72 characters with at least one letter and one number. Lock time 15 minutes. Reset link valid 60 minutes, works once, and ends all refresh tokens of that user.
- One general error message for a wrong e-mail, a wrong password and an inactive account. For an unknown e-mail still compare against a fake hash so the answer takes the same time.
- Forgot password always answers "If this e-mail is registered, a link has been sent".
- Register ignores a role sent by the client. The role is always customer.
- In development the e-mail sender prints the reset link to the server console and keeps the message in memory so that tests can read it.
- authenticate, requireRole and assertBranchAccess middleware are built here. Rate limit on the auth routes.
- On the web: all callers share one refresh request (React StrictMode runs effects twice in development).

## Server work
Register, login with lockout, refresh with rotation, logout, forgot and reset password, read and update my account, change password, list my notifications (and mark one as read).

## Screen work
Register, log in, forgot password, reset password, my account (details and change password), the notification list, route guards by role.

## Not in this slice
Admin screens, user management, role assignment, e-mail verification, any business feature.

## Done when
1. You can register, log in, reload the page and stay logged in, log out, and reset a password with the console link.
2. A wrong password and an unknown e-mail show the same message.
3. Five wrong passwords lock the account; the locked message is clear and honest.
4. A customer who opens a staff address is refused (screen and server).

## Tests that must exist (AT-01 to AT-09)
- Normal: register then log in. Refresh keeps the user logged in. A reset link works once.
- Refusals: duplicate e-mail. Weak password. Same message for wrong password and unknown e-mail. Lockout after five failed logins. An old refresh token used twice ends the whole family. Reset link after expiry or after use. No token gives 401. A wrong role gives 403.
- The database holds only hashes of tokens, never the raw value.
